# Tool-Using LLM Agents: Paradigms, Training, Evaluation, Embodiment and Security

## TL;DR

- The canonical formulation of a tool-using agent augments the action space with language-space "thought" actions that do not affect the environment [1], and two 2023 surveys fixed the field's vocabulary of controller, tool set, environment and human [2][3].
- Capabilities are taught either by self-supervised API-call labelling [4] or by instruction-tuning data distilled from strong teachers over real APIs; ToolLLM's pipeline covers 16,464 real RESTful APIs in 49 RapidAPI categories and casts planning as depth-first search over a decision tree [5], while Gorilla fine-tunes a LLaMA-based model and evaluates generated calls with AST sub-tree matching [6].
- Evaluation repeatedly shows a wide human–agent gap. The best GPT-4-based WebArena agent reached a 14.41% end-to-end task success rate against 78.24% for humans [7]; GAIA reported 92% for human respondents versus 15% for GPT-4 equipped with plugins [8]; the best model on OSWorld succeeded on 12.24% of tasks while humans exceeded 72.36% [9].
- Beyond text APIs, the dominant mechanism is vision-centric grounding: screenshots annotated with element marks (WebVoyager) or OCR plus Grounding DINO and CLIP (Mobile-Agent) mapped to low-level click/type/scroll primitives [10][11], while multi-agent frameworks split it by role, procedure or conversation [12][13][14].
- Security is the least settled area. Indirect prompt injection through tool outputs and retrieved content reaches high attack success in several benchmarks [15][16], tool-description poisoning against live MCP servers reached a 72.8% attack success rate for one model [17], and one 2026 audit argues that published attack-success numbers are frequently inflated by harness defects [18].

## Background

A tool-using LLM agent is a system in which a language model does not merely emit an answer but repeatedly selects and executes external operations — search, calculators, code interpreters, REST APIs, or GUI actions — and conditions its next step on the returned results. The framing is usually attributed to work that augments the model's action space: ReAct interleaves reasoning traces with task-specific actions so that thoughts "do not affect the external environment, thus leading to no observation feedback," and explicitly criticises chain-of-thought as a "static black box" that "is not grounded in the external world" [1]. Two surveys published weeks apart in 2023 consolidated this into a research programme. Tool Learning with Foundation Models names the paradigm, describes a general framework comprising "the controller (typically modeled using a foundation model), tool set, environment, perceiver, and human," and distinguishes learning from demonstrations from learning from feedback [3]. Augmented Language Models defines augmentation as combining reasoning (decomposing a complex task into subtasks) with tool use (calling external modules such as a code interpreter) [2].

The significance of the paradigm is that it moves capability out of parameters and into interfaces. A small model that can call a calculator, a search engine and a calendar can outperform much larger models on knowledge-heavy tasks; Toolformer reports that its approach yields "substantially improved zero-shot performance across a variety of downstream tasks, often competitive with much larger models, without sacrificing its core language modeling abilities" [4]. The same architecture, however, is what creates the agent's distinctive failure surface: once retrieved text becomes an input to control flow, the model must separate instructions from data, which the classic indirect-prompt-injection paper identifies as the root cause when it observes that LLM-integrated applications "blur the line between data and instructions" [19].

The paradigm's immediate ancestry is prompting-only decomposition. Chain-of-thought prompting showed that supplying a few intermediate reasoning exemplars elicits multi-step reasoning, with eight exemplars letting a 540B-parameter model reach state-of-the-art accuracy on GSM8K [20]. Self-ask formalised decomposition into explicit follow-up questions, which has the advantage that it "disentangles the decomposition of the full question... from the actual answers" and lets an external search engine be plugged in for the sub-questions [21]. Least-to-most prompting breaks a problem into a sequence of easier subproblems solved in order, motivated by the observation that chain-of-thought prompting "often performs poorly on tasks that require generalization of solving problems harder than the demonstration examples," and reported at least 99% accuracy on SCAN's length split from just 14 exemplars where chain-of-thought achieved 16% [22]. Tool use can therefore be read as decomposition plus execution: the sub-question machinery already existed, and agents added the ability to actually run something.

## From prompting to acting: the canonical agent loop

The step from decomposition to agency is the interleaved loop. ReAct's formulation is simple but consequential: a thought is an action in language space that changes no external state, an environment action changes state and returns an observation, and the model alternates between them. The empirical payoff in the original paper came from grounding: querying a Wikipedia API overcame hallucination and error propagation in chain-of-thought reasoning, and ReAct "outperforms imitation and reinforcement learning methods by an absolute success rate of 34% and 10% respectively" [1]. Notably, the authors found the best configuration combined ReAct with chain-of-thought rather than replacing it, an early signal that reasoning and acting are complements, not substitutes.

Two refinements appeared quickly. Tree of Thoughts generalises chain-of-thought into deliberate search over coherent "thoughts," adding self-evaluation of candidate states plus lookahead and backtracking, and reports solving 74% of Game of 24 tasks where GPT-4 with chain-of-thought solved 4% [23]. The other refinement concerns faithfulness: a study of decomposition-based reasoning found that factored decomposition, which answers each sub-question in a fresh context, "may improve faithfulness by reducing biased reasoning (how much LLMs rely on unverbalized biases)," and situates itself in a family with least-to-most and successive prompting [24]. The same decomposition rhetoric, in other words, serves both capability and auditability goals — a theme that recurs in the guardrail literature reviewed below.

By 2024 these components were being treated as standard building blocks rather than research novelties. A lightweight agent library describes the field's trajectory as moving "from the simple chain-of-thought prompting to more complex ReAct and Reflection reasoning strategy," with architectures simultaneously evolving "from single agent generation to multi-agent conversation" [25]. That sentence is best read as a period marker: prompting patterns had stabilised into a component vocabulary, and the open questions moved to training data, tools and environments.

## Teaching tool use: self-supervision versus distilled instruction data

Two training philosophies dominate. The first is self-supervision: Toolformer trains a model "to decide which APIs to call, when to call them, what arguments to pass, and how to best incorporate the results into future token prediction," requiring "nothing more than a handful of demonstrations for each API," across a toolset including a calculator, a question-answering system, two search engines, a translation system and a calendar [4]. Its contribution is primarily methodological — it removes the need for large human-annotated call traces — and the retrieved material reports improved zero-shot performance rather than specific accuracy tables.

The second philosophy is distillation at scale over real APIs. ToolLLM constructs ToolBench automatically using ChatGPT in three stages (API collection, instruction generation, solution-path annotation), collecting "16,464 real-world RESTful APIs spanning 49 categories from RapidAPI Hub," and introduces a depth-first search-based decision tree to annotate solution paths that explore multiple reasoning traces [5]. Its automatic evaluator ToolEval reports a pass rate, measuring whether an instruction can be executed within a limited budget, and a win rate; in the paper's comparison table ToolBench contains 126,486 instances and 469,585 real API calls against APIBench's 1,645 APIs and zero real API calls [5]. Gorilla takes the complementary route of fine-tuning rather than prompting: a LLaMA-based model is fine-tuned with self-instruct question generation plus document retrieval and claimed to surpass GPT-4 at writing API calls, with APIBench built by scraping HuggingFace, TorchHub and TensorHub (925 HuggingFace models scraped, 626 after filtering, 1,645 API calls converted into JSON), and evaluation performed by AST sub-tree matching to measure both functional correctness and hallucination [6].

The two families now converge on data quality and optimisation rather than data volume. A 2024 framework argues that tool-use supervised fine-tuning suffers because "training data can inadvertently impede tool-use behavior, token importance is distributed unevenly, and errors in tool calls fall into a small set of distinct categories," and responds with dynamic token weighting plus an error-category reward optimised by proximal policy optimisation, reporting performance matching or surpassing open- and closed-source models "using only 1,217 training data points" when applied to CodeLLaMA-2-7B [26]. The pattern is instructive: the annotated-call corpus is treated as a fixed resource to be reweighted, not expanded.

## Evaluating agents: environments, headline numbers and measurement validity

Benchmarks for tool-using agents split into web, code, assistant, scientific and interactive categories, and their headline numbers are best read as gap measurements rather than scores. WebArena provides a self-hosted environment with four functional websites covering e-commerce, social forum, collaborative software development and content management, plus utilities such as a map and calculator, and 812 long-horizon tasks graded by functional correctness; its best GPT-4-based agent achieved 14.41% end-to-end success versus 78.24% for humans, with the shortfall attributed to "a lack of crucial capabilities such as active exploration and failure recovery" [7]. SWE-bench draws 2,294 software-engineering problems from real GitHub issues across 12 popular Python repositories, filtering roughly 90,000 pull requests down to instances with fail-to-pass tests, and reports that the best-performing model, Claude 2, "is able to solve a mere 1.96% of the issues" [27]. GAIA asks real-world questions requiring reasoning, multi-modality, web browsing and general tool-use proficiency, devising 466 questions and retaining answers to 300 for a leaderboard; human respondents reached 92% while GPT-4 equipped with plugins reached 15%, and even with tools GPT-4 did not exceed 30% on the easiest level and 0% on the hardest [8]. MLE-bench curates 75 Kaggle competitions and finds that the best configuration, o1-preview with AIDE scaffolding, achieves at least a Kaggle bronze medal in 16.9% of competitions, doubling to 34.1% under pass@8, with GPT-4o scoring 8.7% given 24 hours and 11.8% given 100 hours [28].

Two trends cut across these results. First, multi-environment and interactive benchmarks expose reliability rather than peak capability: AgentBench spans eight distinct environments across code, game and web groundings and tested 29 API-based and open-source models, reporting a significant performance disparity between leading systems and open-source competitors no larger than 70B, and noting that "training on code present ambivalent impacts on different agent tasks" [29]. tau-bench emulates dynamic conversations between a language-model-simulated user and an agent with domain APIs and policy guidelines in retail and airline domains, compares the final database state to an annotated goal state, and introduces pass^k to measure reliability across trials; gpt-4o achieved roughly 61% pass^1 on retail and roughly 35% on airline, falling to about 25% for pass^8 on retail [30]. Second, the benchmark literature is now auditing itself. A 2025 meta-work proposes the Agentic Benchmark Checklist with guidelines "that reduce performance overestimation and improve evaluation rigor" [31], and task-specific tool-use evaluation continues to broaden, with a 2026 omni-modal benchmark for professional tool-using agents based on closed-loop verification [32].

The measurement lesson is sharpest in security, but it applies here too: an evaluation harness is an instrument, and an unvalidated instrument produces confident numbers that do not replicate. Any single success rate cited above should be treated as a property of a particular scaffold, prompt and environment, not of the underlying model.

## Embodiment: computer-use, mobile and multimodal agents

When the tool is a graphical interface, perception becomes the bottleneck. WebVoyager builds a large-multimodal-model web agent that completes instructions on live websites, observing screenshots and interactive HTML, and marking interactive elements on the screenshot following Set-of-Mark prompting; the action loop forms a "thought on what action to take (such as clicking, typing, or scrolling)" and the system reports 59.1% task success against 30.8% for GPT-4 with all tools and 40.1% in a text-only setting, with a GPT-4V evaluator agreeing with human judgement 85.3% of the time [10]. The contrast it draws with SeeAct — that the best SeeAct agent "still relies on a finetuned cross-encoder model to select candidate elements" while WebVoyager needs no extra module — illustrates that the design space separates perception plumbing from the reasoning policy.

Mobile-Agent pushes the same principle further by removing system metadata entirely: it "solely relies on device screenshots without any system code, which is a purely vision-based solution," locating text with OCR and icons with Grounding DINO plus CLIP, planning each step from a system prompt, the operation history and the current screenshot, and adding self-reflection so that when "the screenshot has not changed after a particular operation, or the screenshot shows a wrong page," the agent is instructed to try alternatives, across eight defined operations [11]. OSWorld formalises desktop computer use as a partially observable process with screenshot and accessibility observations and raw keyboard and mouse actions such as a right-click at pixel coordinates, providing 369 real tasks and 134 unique evaluation functions; humans accomplished over 72.36% of tasks while the best model achieved 12.24% success, "primarily struggling with GUI grounding and operational knowledge," and the paper's own ablation notes that feeding higher resolution and more trajectory history could roughly double performance while requiring longer context [9]. AndroidWorld offers a fully functional Android environment with programmatic rewards for 116 tasks across 20 real apps and dynamically parameterised instances; its M3A baseline reached 30.6% against a human success rate of 80.0%, and it reports the counterintuitive finding that "while multimodal perception can improve performance in some cases, it generally does not outperform the text-only approach" [33].

The most recent shift is that tools and pixels have become alternatives rather than layers. A 2025 benchmark for computer-use agents lets the agent choose at each step between external MCP tools and direct GUI actions, curating 158 high-quality MCP tools across 7 apps plus 25 distractor tools applicable to 69% of its tasks; introducing tools raised OpenAI o3 from 8.3% to 20.4% at 15 steps and Claude 4 Sonnet from 40.1% to 43.3% at 50 steps, yet even the strongest models had low tool invocation rates at 36.3%, and "the composition of multiple tools remains a significant challenge" [34]. This is a useful corrective to tool-use boosterism: giving a computer-use agent an API does not automatically mean it will use it, and chaining several correctly is a distinct skill from calling one.

## Multi-agent decomposition of tool use

The frameworks that scale tool use across agents differ mainly in how they impose structure. AutoGen treats conversation as the control plane: it defines conversable agents that "can leverage LLMs, human inputs, tools, or a combination of them," instantiates built-in roles such as an LLM-backed assistant and a user proxy that solicits human input or executes code and function calls, and drives decentralised flow through auto-reply, where "once an agent receives a message from another agent, it automatically invokes generate_reply and sends the reply back to the sender unless a termination condition is satisfied," with an optional group chat manager selecting the next speaker [12]. MetaGPT instead encodes standardised operating procedures into prompt sequences so that specialised roles "verify intermediate results and reduce errors," uses an assembly-line paradigm to break tasks into subtasks, requires structured artefacts such as requirements documents, design artefacts, flowcharts and interface specifications, and adds an executive feedback mechanism that debugs and runs code at runtime, reporting a 5.4% absolute improvement on MBPP from that feedback and Pass@1 of 85.9% on HumanEval and 87.7% on MBPP [13]. Its motivation is explicitly reliability: naive chaining risks cascading hallucination, which the structured-artefact discipline is meant to suppress.

Two further designs sharpen the cost-benefit trade-off. CAMEL uses role-playing with inception prompting, in which agents prompt each other toward task completion while staying consistent with human intentions; its design is motivated by named failure modes — "role flipping, assistant repeating instructions, flake replies, and infinite loop of messages" — and it reports that role-playing solutions outperform single-shot gpt-3.5-turbo answers in both GPT-4 and human evaluations [35]. AgentVerse runs a four-stage group process of expert recruitment, collaborative decision-making, action execution and evaluation; its recruiter agent generates expert descriptions dynamically, and group composition adjusts on evaluation feedback. It distinguishes a horizontal democratic structure "especially effective in scenarios like consulting and tool using" from vertical solver-plus-reviewer structures suited to mathematics and software, and documents emergent volunteer, conformity and destructive behaviours [36].

A cleaner separation of concerns appears in work that partitions the tool pipeline itself. One framework decomposes tool use into a planner, a caller and a summariser, each implemented by its own LLM, where the caller is directed by the planner's rationale to invoke specific tools and the summariser crafts the final answer; the motivation is operational — "the tools could be updated frequently in practical scenarios, when the entire LLM requires potential retraining" — and the training recipe first fine-tunes a backbone on undifferentiated data, then clones it into the three roles [14]. A 2025 survey generalises these choices along five dimensions: actors, types such as cooperation, competition or coopetition, structures such as peer-to-peer, centralised or distributed, strategies such as role-based or model-based, and coordination protocols, framing the shift "from isolated models to collaboration-centric approaches" [37].

## Security and reliability of tool-using agents

The defining security problem is that tool outputs are untrusted text entering the control path. The foundational paper on indirect prompt injection showed that adversaries can "remotely (without a direct interface) exploit LLM-integrated applications by strategically injecting prompts into data likely to be retrieved," that processing retrieved prompts "can act as arbitrary code execution, manipulate the application's functionality, and control how and if other APIs are called," and that such prompts "may act as computer worms that spread the injection to other LLMs," concluding that effective mitigations were then lacking [19]. Benchmarks quantified the exposure. InjecAgent built 1,054 test cases with 17 user tools and 62 attacker tools across 30 agents and reported that prompted GPT-4 reached a 23.6% attack success rate in the base setting and 47.0% in the enhanced setting, with prompted Llama2-70B exceeding 80%, while fine-tuned GPT-4 and GPT-3.5 reached only 3.8% and 6.6% — evidence that "fine-tuned agents are more resilient to such attacks compared to prompted agents" — and that the data-transmission step of exfiltration was the easiest, at 100% success for fine-tuned GPT-3.5 and GPT-4 [15]. AgentDojo reported that current LLMs solve fewer than 66% of its tasks even with no attack, that its attacks succeeded against the best agents in under 25% of cases, and that adding a secondary attack detector dropped the attack success rate to 8%, while warning that existing techniques "are not able to provide guarantees for security-critical tasks" [38].

The MCP ecosystem added a distinct vector in which the tool's metadata, not its output, carries the payload. A 2025 disclosure described tool poisoning as embedding "malicious instructions... within MCP tool descriptions that are invisible to users but visible to AI models," exploiting the fact that users see a summarised tool name while models see the complete description, and named rug pulls, where "a malicious server can change the tool description after the client has already approved it," and tool shadowing, where a malicious server modifies the agent's behaviour toward a trusted service without the agent ever calling the attacker's tool [39]. A benchmark over 45 live MCP servers, 353 authentic tools and 1,348 malicious cases found attack success rates exceeding 60% for several models, including 72.8% for o1-mini, observed that "more capable models are often more susceptible, as the attack exploits their superior instruction-following abilities," and reported that agents rarely refuse such attacks, with the highest refusal rate below 3% [17]. It also drew a useful boundary: repurposing indirect-prompt-injection payloads into tool descriptions yielded a near-zero success rate, indicating that metadata poisoning is a separate failure mode from output injection [17]. The OWASP community page frames the same weakness structurally — a "trust gap between connect-time and runtime," since descriptions are reviewed once at connection while responses enter the model context unchecked — and notes that system-prompt restrictions are "enforced only by the LLM's instruction-following, not by backend access controls" [40].

Defences that report the largest effects are architectural rather than textual. A 2026 threat model enumerating fourteen attack vectors across user input, tool outputs, inter-agent messages and orchestrator manipulation found that indirect injection via tool outputs succeeded in 43% of attempts and inter-agent injection in 31%, and that message signing with provenance cut inter-agent injection from 31% to 2.8%, boundary sanitisation cut indirect injection from 43% to 9.5% at a mean latency cost of 12 milliseconds, and privilege-scoped tool access mitigated all observed privilege-escalation attempts; the combined stack reported a 4.2% residual success rate against a 31.2% aggregate baseline, prompting the claim that "system-prompt guardrails fail because they operate at the layer attackers manipulate" [16]. Protocol-level guidance points the same way, prescribing that clients execute MCP server commands "in a sandboxed environment with minimal default privileges," restricting filesystem and network access, using platform sandboxing technologies, warning that servers run with the same privileges as the client, and stating that possession of a state handle must not be treated as authentication [41].

Reliability work has converged on similar conclusions for non-adversarial failures. A taxonomy of agent failures classifies modes across memory, reflection, planning, action and system-level operations, motivated by the observation that "a single root-cause error propagates through subsequent decisions, leading to task failure," and its corrective-feedback agent reports 24% higher all-correct accuracy and 17% higher step accuracy than the strongest baseline, with up to 26% relative improvement in task success [42]. Step-level guarding is one live design: a guardrail model detects unsafe tool invocations before execution by reasoning over interaction history and assessing request harmfulness and action-attack correlations, and the accompanying flow is reported to reduce harmful tool invocations of ReAct-style agents by 65% on average while improving benign task completion by about 10% under prompt injection [43]. A verifiable variant extracts action-based probabilistic rule circuits from policy documents and checks trajectories with executable code, reporting 11.3% average improvement over prior methods at 90.1% recall while reducing API queries by 64.7% and inference time by 58.2% [44]. At the interaction layer, one 2026 paper observes that frameworks "typically assume that tool calls are atomic and return binary success or failure signals," whereas real systems exhibit "timeouts after dispatch, delayed visibility, and partial state updates," and proposes a verification-aware wrapper with postcondition verification, verify-before-retry logic and idempotency keys that reduces duplicate actions while maintaining comparable task success [45]. Prompt-level countermeasures are weaker: a Docker-sandboxed evaluation of tool-description poisoning found defences "largely ineffective and can, counterintuitively, even be counterproductive," a phenomenon the authors name the Firewall Fallacy, and observed a supply-chain trust asymmetry in which attacks against familiar tools were more effective than attacks introducing new ones [41].

## Trends and open problems

Several arcs are visible across the retrieved literature. The first is a migration of effort from the reasoning policy to the infrastructure around it. The prompting questions of 2022 — how to decompose, how to interleave thoughts and actions — were largely settled into reusable components by 2024 [25], and the live work now concerns tool registries, invocation semantics, sandboxing and verification [34][41][45]. A second arc is the rise of metadata and identity as an attack surface: as agents connect to third-party tool servers, the description of a tool becomes executable influence over the agent, and the reported asymmetry between high attack success and near-zero refusal rates suggests that alignment-trained refusal does not transfer to authorised tool use [39][17]. A third is the move toward mixing modalities of action — the same agent choosing between an API and a click — which introduces a new evaluation problem, since multi-tool composition remains the weakest case even when single tool invocation improves results substantially [34].

The clearest disputed result concerns the security numbers themselves. A 2026 audit of an indirect-prompt-injection benchmark and its harness identifies four defect classes, including silent payload non-delivery, scoring attack success by tool identity rather than by arguments, harness scoring that conflates false rejections with model incapacity, and the absence of an audit trail; it quantifies the resulting distortion: "the tool-identity scorer reports a 21.7% attack-success rate where the true argument-level rate is 1.2%," while a model previously reported at 62.8% registers 0% under the corrected harness and a model deemed incapable of tool use turns out to be capable once the environment mismatch is fixed [18]. Since the same paper argues that evaluation validity is a prerequisite for defence claims, all attack-success rates quoted in this survey — including the 23.6%/47.0% figures for prompted GPT-4 [15], the 43% multi-agent tool-output rate [16], and the 72.8% MCP poisoning rate [17] — should be read as instrument-dependent measurements rather than comparisons across a common scale. This is not a reason to dismiss the underlying vulnerability, which is demonstrated across independent benchmarks and live servers, but it does mean the field currently lacks a shared measurement standard.

Benchmark validity is contested more broadly. The Agentic Benchmark Checklist exists because agentic evaluation tends to overestimate performance [31], and the pattern of large pass^1 versus pass^k gaps in interactive settings [30] plus the large gains from simply increasing resolution, context or attempt budget [28][9] together imply that headline success rates measure a configuration as much as a capability. The frequency with which benchmarks are published and then superseded also means that several 2023 figures cited here, such as WebArena's 14.41% [7], SWE-bench's 1.96% [27] and GAIA's 15% [8], should be read as historical baselines rather than current state of the art; the survey did not retrieve the later leaderboards needed to update them.

Open problems that the retrieved evidence leaves unresolved include detecting injected instructions inside free-text tool responses, which the OWASP page explicitly flags as unsolved beyond obvious schema-validation cases [40]; providing guarantees rather than probabilistic defence, which AgentDojo states existing techniques cannot do [38]; reconciling the preference for fine-tuned agents' greater injection resistance [15] with the finding that stronger instruction-following models are more susceptible to metadata poisoning [17]; and validating tool-use reliability outside simulated environments, since the verification-aware wrapper was tested only with injected non-atomic failures in a controlled setting [45]. A further methodological gap is tool hallucination in the strict sense of fabricating non-existent tools or parameters, which the retrieved material supports only indirectly through failure taxonomies and schema-drift discussion [42][16]. Finally, the multi-agent frameworks report genuine gains on structured tasks [13][14] alongside named pathologies such as destructive emergent behaviour [36] and infinite role-play loops [35], and no retrieved source establishes which decomposition is preferable under a fixed compute budget — a comparison the field still needs.
